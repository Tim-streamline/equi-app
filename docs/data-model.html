Full data model

101 tables, grouped by domain. Diagrams show primary and foreign keys; expand a table below each diagram for every column and deletion rule. Grey reference nodes belong to another domain. Large diagrams can be scrolled horizontally.

Horse → protocol → intake: a horse has a history of protocols, at most one active at a time. Every protocol has exactly one intake for that horse. One subscription unlocks app features; protocols are separate purchases, each creating its own intake. Library credits remain separate.

This is the implemented target schema, verified in the test database. Existing databases must pass the legacy-data audit before enforcement.

                                                      Application-level references

                                                      These links are not database foreign keys. Legacy entitlement booking_id retains the consumed intake ID even after deletion. Intake answer section_id and field_id are stable questionnaire keys, not UUID foreign keys. A moved question uses intake_fields.answer_section_key to keep its original answer and attachment namespace while its section_id selects the editable presentation section. Polymorphic references (such as audit targets, moderation subjects and media owners) resolve according to their type fields. JSON columns store structured answers, snapshots, layouts or settings; their internal fields are not separate relational tables. The PHP models and PowerSync schema expose portions of this authoritative PostgreSQL model.

                                                      The conditional unique index permits one active protocol per horse; completed, paused, draft and archived history is not subject to that index. The composite intake FK enforces the same horse on both sides, and deferred triggers enforce a required intake at transaction commit.
